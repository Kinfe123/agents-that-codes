# Access Control

The project has role, email, or IP allowlist and blocklist access controls.
## What This Is
Access control defines who can open and operate the administrative surface. This page explains the relationship between roles, explicit email allowlists, IP rules, and the default behavior when no rule matches.
## Why It Matters
Access Control matters because it is part of how Coding Agent Template turns repository behavior into a usable developer or operator workflow. This page gives readers the mental model first, then uses implementation evidence as supporting context.
## Core Concepts
- roles
- allowlist
- blocklist
- admin access
- IP rules
## Typical Workflow
1. Decide whether access is controlled by role, email, IP, or a combination.
2. Configure allow and block rules before exposing the route in production.
3. Test denied and allowed users so operators understand the security boundary.

### Security Considerations
- **Environment Variables**: Never commit `.env` files to version control. All sensitive data should be stored in environment variables.
- **API Keys**: Rotate your API keys regularly and use the principle of least privilege.
- **Database Access**: Ensure your PostgreSQL database is properly secured with strong credentials.
- **Vercel Sandbox**: Sandboxes are isolated but ensure you're not exposing sensitive data in logs or outputs.
- **GitHub Token**: Use a personal access token with minimal required permissions for repository access.
